# 坏例模板 · 复制后逐项填写

> 一个坏例 = 一条教训 + 一条可执行预防。只出机制，不出实体。

## 编号 / 标题

- 编号：`X-YYYYMMDD-序号`
- 标题：
- 状态：`design` / `public-source` / `verified` / `production`
- 核对日期：YYYY-MM-DD

## 现象（一句话，脱敏）

当时发生了什么、造成了什么返工/误判/泄漏。不含实体名。

## 根因

为什么会发生。区分「表面原因」和「机制性根因」——后者才可复用。

## 预防（可执行）

写具体动作，不写「以后注意」。能变成脚本 Gate / hook / 规则的，注明升级路径。

## 执行教训（通用化）

提炼成一条可迁移的判断规则或自查问句，让别的场景也能用。

## 证据

- 本机实测：命令 / 输出 / 截图位置；没有写「无」。
- 公开来源：原文链接 + 发布方 + 核对日期。
- 时间线：保留决策先后，不改历史口径；相对周次表述。

## 升级状态

- [ ] 仅记录（证据不足，不升硬规则）
- [ ] 可升为规则 / hook / 脚本 Gate（注明哪份规则文件）

## 脱敏自检（全部勾掉才入库）

- [ ] 无接口名 / 类名 / 内部仓名 / 内网域名 / 客户名 / 人名
- [ ] 无具体业务数据 / 问题编号 / commit hash
- [ ] 时间改相对周次，数量不含可定位规模
- [ ] 数字均标注来源与验证程度
